# 详细设计：RBAC 部门数据隔离与跨部门调拨流程

为“操作员 (operator)”角色引入严格的部门隔离机制，并配套规范的跨部门资产调拨（Transfer）工作流。

## 核心需求
1.  **部门 ID 匹配**：所有权限校验基于 `departments.id` 整数。
2.  **多部门管辖**：支持一名操作员管理多个部门（`users.departments` 存储如 `"1,2"` 的 ID 字符串）。
3.  **可见性与安全性隔离**：
    *   **本部门资产**：操作员拥有完全查看和编辑权限（根据业务需要，可限制某些敏感字段）。
    *   **非本部门资产**：操作员**默认不可见**。通过扫码发现时，仅显示“脱敏信息”（资产名称、编号、当前归属），不可查看详情或日志。
4.  **跨部门调拨申请流**：
    *   操作员发现非本部门资产时，可点击“申请调拨”。
    *   **需管理员审批**：所有跨部门变动必须由 Admin 角色在中控台审批通过后生效。
5.  **权限收紧**：
    *   操作员禁止直接新增资产（需由管理员统一入库或赋予特定录入员权限）。
    *   操作员禁止查看全局审计日志。

## 实施细节

### 数据模型扩展
*   **调拨申请表 (`transfer_requests`)**:
    *   `id`: 自增主键
    *   `asset_id`: 关联资产
    *   `from_dept_id`: 原部门
    *   `to_dept_id`: 目标部门（申请人所属部门之一）
    *   `requester_id`: 申请人
    *   `reason`: 申请事由
    *   `status`: 状态（`pending` 待审, `approved` 已准, `rejected` 已驳回）
    *   `timestamp`: 申请时间

### 后端 API 变更

#### 1. `GET /api/assets/:code` (增强扫码识别)
*   若资产不属于操作员管辖：返回 `403` 但携带 `limited: true` 和极简数据，提示“此资产属于 X 部门，您无权查看详细信息，可发起调拨申请”。

#### 2. `POST /api/transfers` (调拨申请)
*   操作员发起。

#### 3. `GET/PATCH /api/transfers` (调拨审批)
*   **Admin 专用**。审批通过时，后端需在事务中执行：
    1.  更新 `assets.dept_id`。
    2.  更新 `transfer_requests.status = 'approved'`。
    3.  向 `inventory_logs` 写入一条特殊的调拨记录。

### 前端 UI 变更
1.  **扫码页 (Scan.tsx)**：识别到他部资产时，展示“申请调拨”弹窗。
2.  **资产列表 (AssetList.tsx)**：对操作员隐藏“新增资产”按钮。
3.  **管理员工作台 (Dashboard/Admin)**：增加“调拨审批”列表模块。
4.  **侧边栏**：根据角色隐藏“审计日志”。

## 安全考虑
*   **防止逻辑漏洞**：只有管理员能修改 `asset.dept_id`。操作员的任何“申请”都不应直接触发数据变更。
